### MOD-1 · Reasoning controls as an API surface: effort levels, thinking budgets and reasoning-state carry-over  — **P1** · THIN · Section B · new turn after Turn 21 (or a substantial rewrite of Turn 21)
*Overlaps gap doc:* #7: context engineering (compaction, context editing) must obey the reasoning-state rules taught here: append-only history, thinking blocks, encrypted reasoning and thought signatures. #11: that item is the lab-side monitorability view, and this is the deployer's API view. This entry also absorbs RAG-2 (RAG lens).
**What it is.** Every frontier API now has a reasoning dial (OpenAI reasoning.effort from none to xhigh/max, Anthropic output_config.effort from low to max with adaptive thinking, Gemini thinking_level), plus opaque reasoning state (encrypted reasoning items, thinking blocks, thought signatures) that must go back unchanged across tool calls and turns. The engineering work is choosing effort per route, knowing each model's defaults and keeping history in a shape the provider accepts.
**Why now.** On Claude Opus 5.5, thinking cannot be turned off, the default effort fell to medium (Opus 5 defaulted to high), and forced tool use (tool_choice any or tool) returns a 400 error [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5). On Claude Fable 5.1 and Opus 5.5, a thinking block replayed after an earlier part of the prompt changed returns a 400 by default only for accounts created on or after 31 Aug 2026 00:00 UTC; older accounts must opt in, and otherwise the failing block passes through [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking). OpenAI says "GPT-5 integrated via Responses scores 5% better on TAUBench compared to Chat Completions, purely by taking advantage of preserved reasoning", with "40–80% better cache utilization" [OpenAI, undated blog, accessed 26 Sep 2026](https://developers.openai.com/blog/responses-api). Azure OpenAI's docs show defaults shifting between versions: gpt-5.1 defaults to effort none, gpt-5.6 on Chat Completions returns an error with function tools unless effort is none, and gpt-5.6 defaults reasoning.context to all_turns, which raises multi-turn token use after an upgrade with no code change [Microsoft Learn, 21 Sep 2026](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning).
**What Vol 2 has today.** Turn 21 covers thinking-token cost (Q98), when not to use a reasoning model (Q99) and says chain of thought "may be hidden or summarised" (Q101), and Turn 91 Q451 lists "controlled reasoning effort" as a cost lever, but nothing covers effort parameters, per-model defaults, reasoning-state carry-over, cache interaction or sampling-parameter limits.
**What to teach.**
- Set effort explicitly on every route, based on an effort sweep on your eval set. Never inherit defaults across model versions. Before building a multi-model cascade, try lower effort on the same strong model; it keeps one cache and one behaviour profile. Compare options by cost per successful task.
- Pass reasoning state back untouched. On OpenAI, pass back all reasoning items, function-call items and function-call outputs since the last user message. For stateless or zero-data-retention (ZDR) use, set store=false and replay encrypted_content [OpenAI, accessed 26 Sep 2026](https://developers.openai.com/api/docs/guides/reasoning). Gemini 3, which introduced thinking_level, returns a 400 when thought signatures are missing from function calling in the current turn [Google Developers Blog, 25 Nov 2025](https://developers.googleblog.com/new-gemini-api-updates-for-gemini-3/).
- Keep history append-only. Anthropic states that "the edits that invalidate thinking are the edits that restart the cache" [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking). Control mismatches with thinking.block_binding.prefix_mismatch_behavior ('error' or 'drop_block', beta header thinking-binding-controls-2026-08-01). Blocks from a model that the target model cannot read are dropped silently. Redact personal data before the first send, use server-side compaction or context editing instead of trimming, and test gateways, data-loss-prevention (DLP) proxies and compaction layers against reasoning models.
- Know what effort changes cost in cache. On Claude, changing top-level effort restarts the cache. Per-message effort (beta header mid-conversation-output-config-2026-07-01) keeps it, but only on Opus 5, Opus 5.5, Fable 5.1 and Mythos 5.1 [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/build-with-claude/effort).
- Know each model's parameter limits. On Azure, GPT-5.x and o-series reasoning models reject temperature, top_p, presence/frequency penalties, logprobs, top_logprobs, logit_bias and max_tokens, while the GPT-6 family accepts temperature, top_p and logprobs [Microsoft Learn, 21 Sep 2026](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning). Claude Opus 4.7 and later (including Opus 5, Opus 5.5, Sonnet 5, Fable and Mythos) return a 400 on any non-default temperature, top_p or top_k [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/build-with-claude/thinking). Gemini 3 accepts temperature, but Google advises keeping it at 1.0 [Google Developers Blog, 25 Nov 2025](https://developers.googleblog.com/new-gemini-api-updates-for-gemini-3/). On Opus 5.5, replace forced tool use with auto plus strict tool use or structured outputs, and expect text between tool calls to arrive as thinking blocks that are empty by default at display 'omitted' [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5).
- Design audits without raw chain of thought (CoT). No Claude display setting returns raw CoT, and requests to reproduce reasoning can be refused under the reasoning_extraction category. Azure warns that extracting raw reasoning "may violate the Acceptable Use Policy" [Microsoft Learn, 21 Sep 2026](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning). Audit summaries, tool calls and outcomes instead.
**Idea to remember.** Reasoning is now a dial plus a state object: set effort per route from evals, and pass reasoning state back untouched and append-only, or pay in 400s, cache misses and silently weaker agents.
**Interview questions.**
1. An agent that worked well on Claude Opus 5 is faster but shallower after a switch to Opus 5.5, with no code change. What happened? — The default effort fell from high to medium, so leaving effort unset now means less thinking. Set effort explicitly per route and re-run an effort sweep on the eval set instead of carrying settings across models.
2. Your AI gateway redacts personal data in earlier turns, or trims old messages, before forwarding requests. What can break with reasoning models? — Reasoning state is bound to the exact history and any edit restarts the prompt cache: on Claude Fable 5.1 and Opus 5.5 a replayed thinking block after a prefix change returns a 400 by default for accounts created on or after 31 Aug 2026 (older accounts opt in or choose drop_block), Gemini returns a 400 when current-turn thought signatures are missing, and OpenAI does not reject trimmed history but stateless/ZDR flows must replay encrypted reasoning items. Redact before the first send, keep history append-only and test the gateway against reasoning models.
3. Cost is too high. Do you route easy traffic to a cheaper model or lower effort on the strong model? — Measure lower effort on the strong model first, because it keeps one cache namespace and one behaviour profile. Do not change top-level effort mid-conversation, since that restarts the cache (use per-message effort where supported), and compare options by cost per successful task.

### MOD-2 · Open-weight serving fidelity: chat templates, tool-call and reasoning parsers, and cross-provider variance  — **P2** · THIN · Section C · new turn after Turn 29
*Overlaps gap doc:* none
**What it is.** The same open-weight checkpoint behaves differently depending on its chat template and response format (for example OpenAI's harmony format), the engine's tool-call and reasoning parsers, the decoding defaults, the quantisation and the engine version. Deploying open models now includes conformance tests against the official API, provider pinning and provider routing based on measured quality.
**Why now.** OpenRouter, drawing on what it calls "billions of LLM tool calls", found that tool use varies between providers of the same weights "significantly more than standard benchmarking would suggest" [OpenRouter, 21 Oct 2025](https://openrouter.ai/blog/announcements/provider-variance-introducing-exacto/). Its Auto Exacto routing cut tool-call errors for GLM-5 from about 8% to about 1% and for gpt-oss-120b from 5.6% to 3.5% (vendor self-reports) [OpenRouter, 12 Mar 2026](https://openrouter.ai/blog/announcements/auto-exacto/). Moonshot's K2 Vendor Verifier (4,000 requests, test run 15 Nov 2025) measured the weakest provider at 50.60% tool-call-trigger similarity to the official API and traced the gaps to old engine versions, a wrong tool-call ID format and missing guided decoding [Moonshot AI, test run 15 Nov 2025](https://github.com/MoonshotAI/K2-Vendor-Verifier). The gpt-oss model card says the models "should only be used with the harmony format as it will not work correctly otherwise" [OpenAI on Hugging Face, card updated 26 Aug 2025](https://huggingface.co/openai/gpt-oss-120b).
**What Vol 2 has today.** Turn 34 Q166 says an application switches between local and hosted models by changing "the base URL and model name", and Turns 30 and 36 cover evals for quantised models and constrained decoding, but nothing covers chat templates, response formats, tool-call or reasoning parsers, or provider variance (searched: chat template, harmony, parser, provider variance).
**What to teach.**
- Explain why identical weights diverge: chat template and response format, tool-call and reasoning parsers, decoding defaults, quantisation and engine version.
- Build a conformance suite against the official API. Measure tool-call trigger rate and schema validity, and include reasoning tasks on your own prompts. Run the vendor's verifier where one exists.
- Pin provider, engine version and template. Track tool-call error rate in production and route by measured accuracy, not price alone.
- Fix the usual causes: current engine versions, the vendor's tool-call ID format (for Kimi K2, functions.func_name:idx) and guided decoding switched on [Moonshot AI, test run 15 Nov 2025](https://github.com/MoonshotAI/K2-Vendor-Verifier).
- Run an import checklist for managed hosting. Amazon Bedrock Custom Model Import applies no default chat template for the OpenAIChatCompletion format, so the template must be in tokenizer_config.json. gpt-oss needs the updated generation_config.json with three EOS (end-of-sequence) IDs [200002, 199999, 200012]; an outdated file "will cause runtime errors". Converse is not supported for GPT-OSS imports [AWS, accessed 26 Sep 2026](https://docs.aws.amazon.com/bedrock/latest/userguide/invoke-imported-model.html).
**Idea to remember.** Same weights do not mean the same model: pin provider, engine version and template, and run a conformance suite against the official API before trusting any endpoint.
**Interview questions.**
1. Kimi K2 scores far below its published agent benchmarks on your chosen provider. What do you check? — Check the engine version, chat template, tool-call ID format, whether guided decoding is on, the quantisation and the decoding parameters. Then run the vendor's verifier or your own conformance set against the official API, and pin or switch provider.
2. How do you choose and monitor a provider for an open-weight model in production? — Shortlist on region, terms and price, then run conformance evals (tool-trigger accuracy, schema validity, reasoning tasks) on your prompts. Pin provider and version, track tool-call error rate in production, and route by measured accuracy rather than price alone.
3. What must you verify when importing gpt-oss into a managed hosting service? — Check that the harmony chat template is in tokenizer_config.json and that generation_config.json carries the current EOS IDs. Then check that the API format you call supports reasoning and tool-call parsing (Bedrock does not support Converse for GPT-OSS imports) and that the reasoning-effort setting is honoured.

### MOD-3 · Uncertainty quantification and selective prediction: calibrated abstain/escalate thresholds, including conformal methods  — **P2** · THIN · Section A · extend Turn 14 (or Turn 64)
*Overlaps gap doc:* none. Cross-lens: RAG-7 (document processing with confidence-routed review) asks how to set the auto-accept threshold, so teach the calibration method once and use document extraction as the worked example.
**What it is.** This topic turns model outputs into calibrated confidence and then into clear decisions: answer, abstain or send to a human. The signals are sample agreement, verifier or judge scores, and logprobs where the API returns them, and thresholds are set on a labelled calibration set with conformal or risk-control methods that bound the error rate on the items handled automatically.
**Why now.** Logprob availability is model-specific and absent on many reasoning APIs: Azure OpenAI's GPT-5.x and o-series reasoning models do not support logprobs, the GPT-6 family supports them again, and Claude has never exposed them [Microsoft Learn, 21 Sep 2026](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning). Conformal factuality (Mohri and Hashimoto) gives 80–90% correctness guarantees with black-box access by backing off to less specific claims [arXiv, 15 Feb 2024](https://arxiv.org/abs/2402.10978). The guarantees hold only while production data resembles the calibration data. As an illustrative caveat rather than settled evidence, a very recent, unreviewed two-author preprint reports coverage falling from 90% to 74% when a model sees unanimous wrong peers [arXiv, 3 Sep 2026](https://arxiv.org/abs/2609.04445).
**What Vol 2 has today.** Turn 14 lists "uncertainty signals" and its Q64 already says "incentives reward guessing" (the point of OpenAI's paper, [arXiv, 4 Sep 2025](https://arxiv.org/abs/2509.04664)), Q180 uses sample agreement as confidence, and Turn 64 and Q240 cover trust and judge calibration, but nothing covers measuring calibration, thresholds with error guarantees or risk–coverage trade-offs (searched: conformal, logprob, semantic entropy, selective prediction).
**What to teach.**
- Pick a confidence signal: sample agreement, a verifier or judge score, or logprobs only where the model returns them. Do not trust a model's stated 0–100 confidence without calibrating it.
- Hold out a labelled calibration set and measure on it how well confidence matches real accuracy.
- Set the auto-accept threshold to meet a target error rate on accepted items, using conformal or risk-control methods. Report coverage (the share automated) next to that error rate.
- Send everything below the threshold to abstention or human review, and show the calibrated confidence in the review UI (Turn 64).
- Recalibrate for every model version and input shift, and monitor realised error and coverage in production.
**Idea to remember.** A confidence score becomes useful only when it is calibrated on your data and turned into a threshold with a measured error rate on the items you let through, and recalibrated whenever the model or inputs change.
**Interview questions.**
1. The customer wants to auto-approve extractions "when the model is confident". How do you design that? — Pick a score (sample agreement, verifier or judge), hold out a labelled calibration set, and use conformal or risk-control methods to choose the threshold that meets the target error rate on accepted items. Report coverage alongside that error rate, and monitor both in production.
2. Why not just ask the model for a 0–100 confidence or use token logprobs? — A model's stated confidence is often miscalibrated, and logprobs are unavailable on many reasoning APIs and score single tokens rather than whole answers. Either way you must calibrate against labels.
3. When do conformal guarantees stop holding? — They stop holding when production data is no longer exchangeable with the calibration data: after distribution shift, a model upgrade, adversarial inputs or multi-agent peer influence (coverage fell from 90% to 74% in a Sep 2026 preprint). Recalibrate per model version and watch realised error.

### MOD-7 · Gap doc #16 (deepened): KV-cache offloading, prompt-cache retention and cache isolation  — **P2** · THIN · Section C · extend Turn 31
*Overlaps gap doc:* #16: this entry is gap doc #16, widened (MOD-7 was merged into it). #16 covers engine-level offloading, and this adds the deployer contract (retention tiers and prices, ZDR defaults, isolation scope) and KV-aware routing. Isolation also touches FDE-10 (multi-tenant isolation).
**What it is.** Serving stacks now keep the KV (key-value attention) cache beyond GPU memory, in CPU RAM, SSD, remote or object storage, and route each request to the replica that already holds its prefix. Providers expose the same mechanism as prompt-cache retention options with their own prices, defaults and isolation scope, so a cache is a cost lever, a latency lever and stored data to govern.
**Why now.** Engines now tier and route the KV cache: NVIDIA Dynamo added a KV-aware router and a KV block manager that offloads to CPU, local storage or object storage [NVIDIA, 18 Mar 2025](https://developer.nvidia.com/blog/introducing-nvidia-dynamo-a-low-latency-distributed-inference-framework-for-scaling-reasoning-ai-models/), and llm-d brought KV-cache-aware routing (about 3x lower mean time to first token, TTFT) and LMCache offloading to Kubernetes [llm-d, 20 May 2025](https://llm-d.ai/blog/llm-d-announce). OpenAI now defaults organisations without zero data retention (ZDR) to 24-hour retention on supported models and ZDR organisations to in-memory [OpenAI, accessed 26 Sep 2026](https://developers.openai.com/api/docs/guides/prompt-caching). Anthropic isolates caches per workspace on the Claude API, Claude Platform on AWS and Microsoft Foundry, but only per organisation on Bedrock and Google Cloud [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/build-with-claude/prompt-caching). An ICML 2025 audit (Gu, Li, Kuditipudi, Liang, Hashimoto) found global cross-user cache sharing at seven API providers, OpenAI among them at that time [arXiv, Feb 2025](https://arxiv.org/abs/2502.07776); OpenAI's guide now says "Caches are not shared across organizations and cannot be reused across regional processing boundaries" [OpenAI, accessed 26 Sep 2026](https://developers.openai.com/api/docs/guides/prompt-caching).
**What Vol 2 has today.** Turn 31 covers prefix caching, chunked prefill and prefill/decode disaggregation (Q152: "Transferring the KV cache between pools") and says to "route sessions consistently", Turn 29 covers PagedAttention and Turn 91 treats prompt caching as a cost lever, but nothing covers offloading tiers, retention options, isolation scope or cache side channels (searched: offload, LMCache, Dynamo, retention, side channel).
**What to teach.**
- Choose retention from your traffic gaps, and keep the prefix byte-stable. Compare the write premium with the input tokens saved per session. Anthropic charges 1.25x for 5-minute cache writes and 2x for 1-hour writes, with reads at 0.1x (0.05x on Opus 5.5, 0.025x on Fable 5.1 and Mythos 5.1) [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/build-with-claude/prompt-caching). OpenAI prices cached tokens at 0.1x on GPT-5.6 and later, and GPT-5.6's prompt_cache_options.ttl accepts only '30m' [OpenAI, accessed 26 Sep 2026](https://developers.openai.com/api/docs/guides/prompt-caching).
- Treat the cache as stored data. OpenAI says caching "may store encrypted key/value tensors in GPU-local storage as application state" [OpenAI, accessed 26 Sep 2026](https://developers.openai.com/api/docs/guides/prompt-caching). Check the retention default under ZDR and the contract terms.
- Verify the isolation scope for each provider and platform (workspace or organisation) instead of assuming it. The 2025 audit showed that cache timing can reveal whether another user sent the same prefix.
- When self-hosting, tier the KV cache (GPU, CPU RAM, SSD, remote storage) and use KV-aware routing so requests land where their prefix is cached. The cost is network transfer and the gain is lower TTFT.
**Idea to remember.** A prompt cache is stored state, not just a discount: pick retention from your traffic gaps, route by prefix, and verify where the KV lives and who shares it.
**Interview questions.**
1. Users pause about 20 minutes between turns and your cache hit rate is near zero. What do you change? — Use a longer retention tier if the write premium pays back (Anthropic's 1-hour cache costs 2x on writes; on OpenAI retention depends on the model and ZDR status, and GPT-5.6 offers only a 30-minute time-to-live, TTL). Keep the prefix byte-stable, keep session affinity through cache keys, and compare cache-write cost with the input tokens saved per session.
2. Why would a zero-data-retention customer ask about prompt caching? — Caching keeps KV tensors derived from their prompts as application state. Check the retention default under ZDR (in-memory on OpenAI), the isolation scope on the chosen platform and the provider's contract terms.
3. When self-hosting, why add KV offloading and KV-aware routing? — Long agent contexts overflow GPU memory and multi-turn sessions reuse prefixes, so offloading keeps KV blocks cheaply and routing sends each request to the replica that already holds them. llm-d reported about 3x lower mean TTFT, paid for with network transfer.

### MOD-9 · Inference nondeterminism and reproducibility (batch invariance)  — **P2** · THIN · Section C · extend Turn 29 (and correct Turns 87, 93 and 97)
*Overlaps gap doc:* none
**What it is.** The same prompt at temperature 0 can return different outputs, mainly because kernel results depend on batch size, which changes with server load. The topic covers what batch-invariant serving modes cost, and how to design evals, audits and regression tests that either remove the variance or measure it statistically.
**Why now.** Thinking Machines sampled Qwen3-235B-A22B-Instruct-2507 1,000 times at temperature 0 and got 80 unique completions (the most common appeared 78 times); with batch-invariant kernels "all of our 1000 completions are identical", at a 1.6–2x slowdown (42 s with an improved kernel and 55 s unoptimised, against 26 s for default vLLM) [Thinking Machines, 10 Sep 2025](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/). SGLang shipped deterministic inference with a 34.35% average slowdown [LMSYS, 22 Sep 2025](https://lmsys.org/blog/2025-09-22-sglang-deterministic/), and vLLM's VLLM_BATCH_INVARIANT=1 mode is in beta and needs GPU compute capability 8.0 or higher [vLLM, accessed 26 Sep 2026](https://docs.vllm.ai/en/latest/features/batch_invariance.html). Temperature is not a universal control either: Claude Opus 4.7 and later, including Opus 5.5, return a 400 on any non-default temperature [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/build-with-claude/thinking), and Azure's GPT-5.x and o-series reasoning models reject it, while the GPT-6 family and Gemini 3 accept it [Microsoft Learn, 21 Sep 2026](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning). These experiments ran on self-hosted engines, and hosted-API customers cannot switch batch invariance on.
**What Vol 2 has today.** Turn 97 Q480 handles CI randomness with "Low temperature, repeated runs, tolerance bands, confidence intervals and pinned judges", and Turns 87 (Q429) and 93 (Q461) say pinning makes behaviour "reproducible", but nothing explains why temperature 0 is nondeterministic or mentions deterministic serving modes (searched: determinis, batch invariance, reproduc).
**What to teach.**
- Explain the root cause. Server load changes batch size, and many kernels (matmul, attention, normalisation reductions) are not batch-invariant, so logits shift slightly and greedy decoding diverges. Seeds and race conditions are not the main cause.
- Decide where batch invariance is worth its cost: self-hosted runs that must be replayable, such as regenerating a decision for an audit or RL pipelines. The measured cost was a 1.6–2x slowdown in the Thinking Machines test and about 34% in SGLang.
- On hosted APIs, store the full inputs, outputs and versions at decision time, and replay the record instead of regenerating.
- Treat evals statistically: several runs per case, confidence intervals, pass^k and tolerance bands, and no reading of single-run diffs as real changes. vLLM's speculative-decoding docs also warn that batch-size changes can vary logprobs [vLLM, accessed 26 Sep 2026](https://docs.vllm.ai/en/latest/features/speculative_decoding/).
- Check whether each model accepts temperature before relying on it (see MOD-1). Describe pinning as "stable and deliberate, not bitwise reproducible".
**Idea to remember.** Temperature 0 is not determinism: outputs depend on who else is in the batch, so buy batch invariance for runs that must be replayable, store outputs for decisions you may need to reproduce, and treat the rest statistically.
**Interview questions.**
1. Why can the same prompt at temperature 0 return different answers? — Server load changes the batch size, and many kernels are not batch-invariant, so logits differ slightly and greedy decoding diverges. It is not mainly a random seed or a race condition.
2. A model-risk team wants you to reproduce last month's decision exactly. What do you say? — Store the full inputs, outputs and versions at decision time and replay the record rather than regenerating. Where regeneration is required, self-host with a batch-invariant mode and pinned engine and hardware, because hosted APIs generally cannot guarantee bitwise replay.
3. How does nondeterminism change your eval practice? — Run each case several times, report confidence intervals and pass^k, and set tolerance bands for regressions. Drop "low temperature" as the default fix, because several current models reject non-default temperature.

### MOD-12 · Classifier refusals and cross-model fallback as a production outcome  — **P2** · THIN · Section I · extend Turn 94 (cross-link Turns 26 and 87)
*Overlaps gap doc:* #9: frontier safety frameworks are the lab-side release gating, and this entry is their runtime consequence for deployers. #1: AI cyber offence and defence explains why security customers hit cyber classifiers. Cross-lens: FDE-8 covers screening use cases against usage policies, not handling refusals at runtime.
**What it is.** Frontier APIs now run safety classifiers per category, and a declined request comes back as a successful response with a refusal stop reason and a category, not as an error. Handling it means detecting refusals by stop reason, routing to a fallback model you have already evaluated, logging which model actually answered, and budgeting for billed refusals and rate-limit use.
**Why now.** Anthropic's docs say Claude Fable 5.1, Fable 5, Opus 5.5 and Opus 5 include safety classifiers, and a declined request returns a normal response with stop_reason "refusal" and a stop_details.category of cyber, bio, frontier_llm, reasoning_extraction or general_harms [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback). The same page says "Benign cybersecurity work", "Beneficial life sciences work" and "Benign machine learning work" can trigger categories; as of Sep 2026, refusals before any output in bio, frontier_llm and reasoning_extraction are billed, and every refusal counts against rate limits. A server-side fallback beta (header server-side-fallback-2026-07-01, fallbacks: 'default') retries on a recommended model that may be less capable, and the response names the model that served it [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback). Opus 5.5 added a biology classifier and the reasoning_extraction category [Anthropic, accessed 26 Sep 2026](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5).
**What Vol 2 has today.** Turn 26 Q124 treats over-refusal as a training-quality metric, Turn 87 Q433 monitors "refusal rates" as a drift signal, and Turn 94 Q466 says fallback models must be "evaluated in advance" but only for outages, while nothing covers classifier refusals as an API outcome, refusal categories, refusal billing or recording which model served the answer (searched: refus, classifier, fallback, stop reason).
**What to teach.**
- Detect refusals by stop reason, not HTTP status, and log the category with each request.
- Evaluate a fallback model for each task in advance, then configure server-side or client-side fallback. Do not blindly retry the same model, because each retry counts against rate limits.
- Record the model that actually served each answer in audit logs, eval results and cost attribution.
- Budget for the refusal rate. Some categories are billed before any output, every refusal uses rate limit, and fallback adds a second request. Use the provider's fallback-credit mechanism so you do not pay twice for the prompt cache.
- Track the refusal rate per category as a production metric. Expect false positives in security, life-sciences and ML-platform work, and report systematic ones to the provider.
**Idea to remember.** A refusal is a normal response, not an error: detect it by stop reason, send it to a fallback you have already evaluated, and log which model really answered.
**Interview questions.**
1. A security customer's triage agent on Claude Opus 5.5 sometimes returns HTTP 200 with no text. What is happening and what do you do? — It is most likely a classifier refusal: stop_reason "refusal" with category "cyber". Branch on the stop reason, route to a fallback you have evaluated for this task, log the category and the serving model, and track refusal rate by category, but do not blindly retry, because each retry counts against rate limits.
2. Why must audit records name the serving model when fallback is enabled? — The answer may come from a different and possibly less capable model. Evals, compliance evidence and cost attribution must reflect the model that actually answered, and the API response names it.
3. How do refusals affect cost and capacity planning? — Some categories are billed even before any output, every refusal counts against rate limits, and fallback adds a second request. Budget for the refusal rate, and use the provider's fallback-credit mechanism to avoid paying twice for the prompt cache.

### MOD-13 · Teacher-model terms and safeguards for distillation and synthetic training data  — **P2** · THIN · Section B · extend Turn 23 (cross-link Turns 77 and 85)
*Overlaps gap doc:* none
**What it is.** Before a model's outputs are used to train a student, generate synthetic fine-tuning data or label data for embeddings, someone must check the teacher's licence and terms. Closed APIs prohibit using outputs to build competing models and detect distillation, and some open-weight licences pass their terms on to any model trained on their outputs.
**Why now.** The Gemma Terms of Use define "Model Derivatives" to include models created by transferring Gemma's patterns, "including distillation methods ... or methods based on the generation of synthetic data Outputs by Gemma", so use restrictions and notice duties flow down to the student [Google, last modified 1 Apr 2026](https://ai.google.dev/gemma/terms). On 23 Feb 2026 Anthropic disclosed industrial-scale distillation by DeepSeek, Moonshot and MiniMax, using about 24,000 fraudulent accounts and over 16 million exchanges, so providers now detect distillation patterns and act on them [CNBC, 24 Feb 2026](https://www.cnbc.com/2026/02/24/anthropic-openai-china-firms-distillation-deepseek.html).
**What Vol 2 has today.** Turn 23 Q110 says sequence-level distillation "works even when only a text API is available" with no caveat about output-use terms, Q112 covers synthetic-data quality and Turn 77 Q382 puts model licences in supply-chain security, but nothing covers competing-model clauses, licence flow-down to distilled students or distillation detection by providers (searched: terms of, competing, derivative, distill with licen).
**What to teach.**
- Read the teacher's output-use terms before any project that trains on model outputs: synthetic data, distillation, labelling, or fine-tuning an embedding model or reranker. Check the competing-model clauses and how the customer's use is scoped.
- Check licence flow-down. Under Gemma's terms, a student trained on Gemma outputs is a Model Derivative and inherits the use restrictions and notice duties.
- Expect generation requests to closed models to be refused or billed under classifier categories, and expect providers to detect traffic that looks like distillation.
- Choose a distillation method the teacher allows. On-policy distillation needs the teacher's per-token log-probabilities on the student's own samples, which chat APIs do not return, so it is practical only with open-weight teachers. Closed teachers limit you to sequence-level distillation on their text, subject to their terms.

**Idea to remember.** A teacher's outputs come with its terms: pick a teacher whose licence allows the student you plan to build, and record the teacher and its licence in the AI-BOM.
**Interview questions.**
1. A customer wants to fine-tune an internal 8B model on data generated by a closed frontier model. What do you check first? — Check the provider's output-use terms (competing-model clauses and how the customer's use is scoped), whether generation requests may be refused or billed under classifier categories, the data-handling terms, and permissively licensed open-weight teachers as an alternative. Get legal sign-off and record the teacher and its licence in the AI-BOM.
2. Why can distilling from Gemma change your student model's obligations? — Gemma's terms count models trained on Gemma outputs, through distillation or synthetic data, as Model Derivatives. Its use restrictions and notice duties therefore flow down to your student.
3. Can you run on-policy distillation with a closed API teacher? — Generally not, because it needs the teacher's per-token log-probabilities on the student's own samples, which chat APIs do not provide. It is practical with open-weight teachers; closed teachers limit you to sequence-level distillation on their generated text, subject to their terms.

### MOD-4 · Reinforcement fine-tuning (RFT) as a managed service: graders, rubric rewards and platform choice  — **P3** · THIN · Section B · extend Turn 22 (move Turn 135's practical Q&As there; no new turn)
*Overlaps gap doc:* none
**What it is.** Hosted reinforcement fine-tuning (RFT) improves a model, usually a smaller one, on a customer's own tasks: the customer supplies prompts and graders (string checks, code or Lambda functions, rubric-based model judges), and the platform runs the reinforcement-learning (RL) loop. Managed RFT is consolidating onto cloud platforms and open weights while OpenAI exits self-serve fine-tuning, and process reward models (PRMs, which score each reasoning step) remain mostly research.
**Why now.** OpenAI opened RFT on o4-mini on 8 May 2025 [OpenAI Developer Community, 8 May 2025](https://community.openai.com/t/fine-tuning-updates-reinforcement-fine-tuning-now-available-gpt-4-1-nano-fine-tuning/1255539), but on 7 May 2026 it announced that it is winding down self-serve fine-tuning, including RFT: no customer can create new jobs from 6 Jan 2027, and o4-mini, its only RFT model, is listed for shutdown on 23 Oct 2026 [OpenAI, accessed 26 Sep 2026](https://developers.openai.com/api/docs/deprecations). Amazon Bedrock launched RFT on 3 Dec 2025 for Nova 2 Lite with rule-based, AI-judge and Lambda graders (its "66% accuracy gains on average" is a vendor claim) [AWS, 3 Dec 2025](https://aws.amazon.com/about-aws/whats-new/2025/12/bedrock-reinforcement-fine-tuning-66-base-models), and added qwen.qwen3-32b and openai.gpt-oss-20b on 17 Feb 2026 [AWS, 17 Feb 2026](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-bedrock-reinforcement-fine-tuning-openai). Microsoft Foundry still offers RFT (o4-mini generally available, GPT-5 in private preview) [Microsoft Learn, accessed 26 Sep 2026](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reinforcement-fine-tuning), and Thinking Machines' Tinker, which runs supervised fine-tuning (SFT) and RL on open weights including Kimi K2 Thinking, reached general availability on 12 Dec 2025 [Thinking Machines, 12 Dec 2025](https://thinkingmachines.ai/news/tinker-general-availability/). Research explains why platforms offer rubric and verifier rewards rather than PRMs: Rubrics-as-Rewards beat Likert-scale judge rewards by up to 31% relative on HealthBench [arXiv, Jul 2025](https://arxiv.org/abs/2507.17746), and Qwen's study found Monte-Carlo-labelled PRM data inferior [arXiv, Jan 2025](https://arxiv.org/abs/2501.07301).
**What Vol 2 has today.** Turn 20 teaches RL with verifiable rewards (RLVR) and the GRPO algorithm as theory, and Turn 135 (Watch) already covers when RL beats prompting or fine-tuning (Q673), reward hacking and the checks against it (Q674) and governance of consent, weight ownership and retraining (Q676), but nothing covers hosted RFT platforms or grader design (searched: reinforcement fine-tuning, grader, rubric, process reward).
**What to teach.**
- Decide when RFT beats prompting and SFT. It fits when outputs can be graded reliably but ideal answers are hard to write, the task has several steps, only hundreds of examples exist, and simpler methods have plateaued on a held-out set.
- Write the grader as the specification. Make the task guess-proof, combine hard rule checks with a rubric judge calibrated against humans, and prefer rubric rewards to a single Likert score.
- Pick a platform that will still exist: Bedrock RFT, Microsoft Foundry RFT, or RL on open weights (for example Tinker). Do not start new work on OpenAI self-serve fine-tuning. It closed to organisations that had never fine-tuned on 7 May 2026, and from 2 Jul 2026 only organisations with recent inference on fine-tuned models can create jobs. Existing OpenAI fine-tunes keep serving only until their base model is deprecated [OpenAI, accessed 26 Sep 2026](https://developers.openai.com/api/docs/deprecations).
- Cover governance: what training data leaves the tenant, who owns the tuned weights, where they are hosted, whether they can move between platforms, and when to re-tune because the base model retires.
**Idea to remember.** In RFT the grader is the specification: if the reward can be gamed or guessed, the model learns the loophole, not the task.
**Interview questions.**
1. When would you choose RFT over SFT? — Choose it when you can grade outputs reliably but cannot easily write ideal answers, the task needs reasoning over several steps, and you have only hundreds of examples. Prompting and SFT should also have plateaued on a held-out set first.
2. How do you design a grader that will not be reward-hacked? — Make the task guess-proof and combine hard rule checks with a rubric judge calibrated against humans. Keep hidden held-out tasks and read sampled trajectories for loopholes before trusting the score.
3. A customer's plan relies on OpenAI's fine-tuning API for RFT. What do you tell them? — OpenAI is winding down self-serve fine-tuning: no customer can create new jobs from 6 Jan 2027, o4-mini (its only RFT model) is listed for shutdown on 23 Oct 2026, and existing fine-tunes serve only until their base model is deprecated. Re-plan on a platform that still offers RFT (Bedrock, Microsoft Foundry) or on open weights, and budget for re-tuning.

### MOD-6 · Microscaling low-precision formats and quantisation-native model releases  — **P3** · THIN · Section C · extend Turn 30 (one paragraph)
*Overlaps gap doc:* none
**What it is.** Microscaling formats are block-scaled 4-bit number formats: MXFP4 (an Open Compute Project standard) shares one power-of-two scale per 32-value block, and NVFP4 shares one FP8 scale per 16-value block plus a per-tensor FP32 scale. Some models now ship already quantised through quantisation-aware training (QAT), such as gpt-oss (MXFP4) and Kimi K2 Thinking (INT4).
**Why now.** gpt-oss was post-trained with MXFP4 weights for its mixture-of-experts (MoE) layers, so the 120b model can "run on a single 80GB GPU (like NVIDIA H100 or AMD MI300X)", and "all evals were performed with the same MXFP4 quantization" [OpenAI on Hugging Face, Aug 2025](https://huggingface.co/openai/gpt-oss-120b). NVIDIA reports NVFP4 as about 3.5x smaller than FP16 and 1.8x smaller than FP8, with "1% or less accuracy degradation versus FP8" on DeepSeek-R1-0528 [NVIDIA, 24 Jun 2025](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/). Kimi K2 Thinking ships native INT4 through QAT as "weight-only quantization to the MoE components", and Moonshot claims a "lossless 2x speed-up" in low-latency mode (a vendor claim) [Moonshot AI on Hugging Face, accessed 26 Sep 2026](https://huggingface.co/moonshotai/Kimi-K2-Thinking). NVIDIA also pretrained a 12B model on 10T tokens in NVFP4, scoring 62.58% on MMLU-Pro against 62.62% for FP8 [arXiv, 29 Sep 2025](https://arxiv.org/abs/2509.25149).
**What Vol 2 has today.** The index lists "FP8, FP4 and low-precision formats — 30", Q144 explains per-group scales, Q145 contrasts weight-only with weight-and-activation quantisation and Q147 says to compare "against the BF16 baseline", but nothing covers microscaling block formats or QAT-native releases that have no BF16 baseline (searched: MXFP, NVFP, microscal, QAT).
**What to teach.**
- Compare MXFP4 and NVFP4: block size (32 or 16 values) and scale type (power-of-two or FP8, plus NVFP4's per-tensor scale).
- Know when native FP4 hardware matters. Weight-only 4-bit formats run on older GPUs through dequantising kernels and still speed up decode, which is limited by memory bandwidth. Native FP4 matrix maths (Blackwell) pays off when activations are also low precision, for compute-bound prefill and high-batch throughput.
- Evaluate QAT-native releases against the vendor's published evals and its official API, because there is no BF16 baseline.
- Check the engine's hardware support matrix, and benchmark real request shapes before choosing a GPU generation.
**Idea to remember.** The number format is part of both the model and the hardware choice: weight-only 4-bit speeds up decode even on older GPUs, native FP4 hardware pays off when activations are low precision too, and a QAT-native release has no BF16 baseline.
**Interview questions.**
1. MXFP4 vs NVFP4? — Both are 4-bit floats with block scales: MXFP4 uses 32-value blocks with power-of-two scales, and NVFP4 uses 16-value blocks with FP8 scales plus a per-tensor scale. Blackwell-class tensor cores run both natively.
2. How do you evaluate a model that is released only in MXFP4 or INT4? — There is no BF16 baseline, so compare your endpoint with the vendor's published evals and its official API, skill by skill, using a conformance and task eval set.
3. Will gpt-oss-120b be slow on an H100, which has no native FP4 maths? — Not necessarily: its MXFP4 quantisation covers only the MoE weights, engines dequantise them in kernels, and memory-bound decode still gains from smaller weights (the model card says it runs on a single 80GB H100 or MI300X). Native FP4 tensor cores matter when activations are also low precision, for compute-bound prefill and high-batch throughput, so benchmark your real request shapes.

### MOD-8 · Serverless GPU inference: autoscaling, scale-to-zero and cold starts  — **P3** · THIN · Section C · extend Turn 33 (one paragraph plus one Q&A on autoscaling signals)
*Overlaps gap doc:* none
**What it is.** Serverless GPU inference runs self-hosted or fine-tuned models on GPU platforms that add and remove replicas with demand, down to zero. The engineering work is the cold-start path (GPU allocation, image pull, weight loading, engine start-up, graph capture) and its mitigations: GPU memory snapshots, streamed weights, engine sleep modes and a floor of warm replicas.
**Why now.** Cloud Run GPUs reached general availability (GA) on 2 Jun 2025 with L4 GPUs, scale to zero and per-second billing; instances start in under 5 s, but Google's figure of about 19 s for gemma3:4b includes "startup time, model loading time, and running the inference" [Google Cloud, 2 Jun 2025](https://cloud.google.com/blog/products/serverless/cloud-run-gpus-are-now-generally-available). Modal's GPU memory snapshots (alpha) cut a vLLM cold start from 45 s to 5 s, but the model was Qwen2.5-0.5B-Instruct, a very small one, so the result does not carry over to production-size models [Modal, 30 Jul 2025](https://modal.com/blog/gpu-mem-snapshots). Amazon Bedrock Custom Model Import removes inactive models and raises ModelNotReadyException on the first invoke while it restores them, and restoration time "depends on the on-demand fleet size and the model size" [AWS, accessed 26 Sep 2026](https://docs.aws.amazon.com/bedrock/latest/userguide/invoke-imported-model.html). vLLM's sleep mode frees "90%+" of GPU memory so that one GPU can switch between models [vLLM, accessed 26 Sep 2026](https://docs.vllm.ai/en/latest/features/sleep_mode.html).
**What Vol 2 has today.** Turn 33 says "idle GPUs quietly multiply the cost of every token", Q160 says "cost per token scales inversely with utilisation" and Turn 93 Q460 covers Kubernetes GPU scheduling, but nothing covers autoscaling signals, scale-to-zero or cold starts (searched: serverless, cold start, autoscal, scale to zero, warm pool).
**What to teach.**
- Weigh the scale-to-zero trade-off: idle cost against cold-start latency, judged against the latency target for the first request after idle.
- Break down where cold-start time goes: node and GPU allocation, container pull, weight download and load, engine start-up, compilation and graph capture, and warm-up.
- Buy cold-start time down with cached images, local or streamed weights, GPU memory snapshots, sleep mode, a warm floor and pre-warming before known peaks.
- On managed import, handle ModelNotReadyException with retries, and warm the model before users arrive.
- Scale on queue depth, in-flight requests or KV-cache use against a time-to-first-token target, not on CPU or GPU utilisation alone.
**Idea to remember.** Scale-to-zero trades idle cost for cold-start latency: know your cold-start budget in seconds, then buy it down with snapshots, streamed weights or a warm floor.
**Interview questions.**
1. A fine-tuned 8B model gets bursty traffic: 50 requests a minute in office hours and near zero overnight. Dedicated GPU or serverless? — Compare utilisation-adjusted cost with the cold start you can tolerate; serverless with one warm replica in office hours and scale-to-zero overnight often wins. If several tenants share a base model, host their LoRA adapters on it instead.
2. Where does cold-start time go for an LLM server, and how do you cut it? — It goes to GPU and node allocation, container pull, weight download and load, engine start-up, compilation and graph capture, then warm-up. Cut it with cached images, local or streamed weights, GPU memory snapshots, sleep mode and pre-warming ahead of known peaks.
3. Which metric should drive autoscaling for an LLM service? — Queue depth, in-flight requests or KV-cache use against a time-to-first-token target. CPU or GPU utilisation alone is misleading, because decoding is limited by memory bandwidth.

### MOD-10 · Small specialised models inside agent systems (SLM-first, fine-tune-to-replace)  — **P3** · THIN · Section B · extend Turn 23 (one paragraph)
*Overlaps gap doc:* none
**What it is.** Narrow, high-volume agent steps (routing, tool-call formatting, extraction, classification, guard checks) move from the frontier model to fine-tuned small language models (SLMs) under 10B or even 1B parameters, with escalation to a large model when needed. It runs as a loop: log calls, cluster them, distil or fine-tune, shadow-test, then swap.
**Why now.** Google released Gemma 3 270M for task-specific fine-tuning, citing a partner's fine-tuned Gemma 3 4B that beat larger proprietary models at content moderation [Google Developers Blog, 14 Aug 2025](https://developers.googleblog.com/en/introducing-gemma-3-270m/), and then FunctionGemma, a 270M function-calling model whose accuracy on the Mobile Actions dataset rose from 58% to 85% after fine-tuning [Google, 18 Dec 2025](https://blog.google/technology/developers/functiongemma/). Thinking Machines reports on-policy distillation reaching 70% on AIME'24 with Qwen3-8B at 9–30x lower cost than RL [Thinking Machines, 27 Oct 2025](https://thinkingmachines.ai/blog/on-policy-distillation/). NVIDIA Research argues that small models suit many agent calls, but its paper is a self-described position paper (now v3, revised 22 Sep 2026), so treat it as advocacy, not evidence [arXiv, Jun 2025](https://arxiv.org/abs/2506.02153). OpenAI's self-serve fine-tuning takes no new jobs from 6 Jan 2027, which pushes this route onto open-weight students [OpenAI, accessed 26 Sep 2026](https://developers.openai.com/api/docs/deprecations).
**What Vol 2 has today.** Turn 23 (P1) covers distillation into a small model for a task, Turn 22 Q103 fine-tunes for "narrow tasks", Turn 21 Q99 and Q102 keep reasoning models off extraction and compare routers with cascades, Turn 91 Q451 lists "model routing" and Turn 121 Q603 says small models suit "Structured, checkable, narrow tasks", so only the operating loop that finds and replaces steps is missing.
**What to teach.**
- Find the candidates. Trace production calls, cluster them by call type, and rank clusters by volume × cost × how automatically the output can be checked.
- Build the student from verified teacher traces mixed with real labels, after checking the teacher's terms (MOD-13). Use on-policy distillation only with an open-weight teacher, because chat APIs do not return per-token logprobs on the student's samples.
- Shadow-test before the swap. Keep confidence-based escalation to the large model, and monitor quality per cluster.
- Plan retraining for when the base or teacher model changes, and host students on open weights rather than on a fine-tuning service that is closing.
**Idea to remember.** Most agent calls are narrow and repetitive: log them, cluster them, and let a fine-tuned small model take each cluster it passes on your evals, keeping the frontier model for the rest.
**Interview questions.**
1. How do you find which agent steps can move to a small model? — Trace production calls, cluster them by call type, and rank clusters by volume, cost and how automatically the output can be checked. Start with checkable, high-volume steps such as routing, extraction and tool-argument formatting.
2. What are the risks of an SLM-first design? — Brittleness outside the training distribution, retraining work whenever the base or teacher changes, and hidden quality loss. Mitigate them with confidence-based escalation to the large model, shadow testing and per-cluster monitoring.
3. Where does the training data for the small model come from? — From verified production traces of the teacher, filtered and mixed with real labels, for sequence-level distillation once the teacher's output-use terms are checked. On-policy distillation needs the teacher's per-token log-probabilities on the student's own samples, which chat APIs do not return, so it is practical only with open-weight teachers.

### MOD-11 · Side effects of fine-tuning and distillation: emergent misalignment and subliminal trait transfer  — **P3** · THIN · Section B · extend Turn 26 (one paragraph; cross-reference Turns 23 and 25)
*Overlaps gap doc:* none
**What it is.** Narrow fine-tunes can change behaviour far outside the training task (emergent misalignment), and students distilled from a teacher with the same base model can inherit its hidden traits through data that looks unrelated, even after filtering (subliminal learning). Evaluation after tuning therefore has to be broad, and choosing a teacher becomes a safety decision.
**Why now.** Betley et al. fine-tuned models to write insecure code without disclosure and saw broad misalignment on unrelated prompts, strongest in GPT-4o and Qwen2.5-Coder-32B-Instruct, and it could be hidden behind a backdoor trigger (ICML 2025; arXiv notes an extended version in Nature, early 2026) [arXiv, 24 Feb 2025](https://arxiv.org/abs/2502.17424). Cloud et al. showed traits, including misalignment, passing from teacher to student through number sequences, code or reasoning traces when both share a base model, but not across different base models [arXiv, 20 Jul 2025](https://arxiv.org/abs/2507.14805). Separately, fine-tuning on 10 unrelated examples recovered most hazardous capabilities in models edited with the RMU unlearning method [arXiv, 26 Sep 2024](https://arxiv.org/abs/2409.18025).
**What Vol 2 has today.** Turn 26 says fine-tuning "can erode" safety, Q126 says safety "can degrade even with benign data; re-run safety evaluations" and Q106 evaluates fine-tunes with "general-ability, format, safety and cost checks", but nothing names narrow-to-broad behavioural generalisation or trait transfer through distillation (searched: emergent misalignment, subliminal, trait).
**What to teach.**
- Explain emergent misalignment and subliminal learning, and why both are still research results.
- After every tune, run a broad behaviour suite against the base model: safety and over-refusal, honesty and sycophancy, instruction hierarchy, and probes for behaviour tied to hidden triggers.
- Treat teacher choice as a safety decision. A teacher with the same base as the student can pass on hidden traits, so prefer verified data or a teacher from a different base when traits matter.
- Keep claims about unlearning modest. Fine-tuning can undo unlearning, which supports Vol 2's position in Turn 52.
**Idea to remember.** A narrow fine-tune is a whole-model change: evaluate broadly after every tune, and do not assume that filtering a teacher's outputs removes the teacher's habits.
**Interview questions.**
1. You fine-tuned a model on a narrow internal task and task metrics improved. What else must you test before release? — Run a broad behaviour suite against the base model: safety and over-refusal, honesty and sycophancy, instruction hierarchy, and probes for behaviour tied to hidden triggers. Narrow tuning can generalise into broad misalignment.
2. What does subliminal learning imply for distillation? — A student that shares the teacher's base model can inherit the teacher's traits through data that looks neutral, and content filtering does not stop it. Vet teachers, evaluate students broadly, and prefer verified data or a teacher from a different base when traits matter.
3. Does using a provider's fine-tuning service remove this risk? — No: providers may screen training data, but the customer owns the evaluation of the tuned model in its application, so re-run the safety and behaviour suites. Also choose a service that will stay open, since OpenAI's self-serve fine-tuning takes no new jobs from 6 Jan 2027.
